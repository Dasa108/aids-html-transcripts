Module 1

What the app does

You'll learnEvery feature the app has, and the path a lecture takes from microphone to flashcard.

Lecture Notes is an Android app for students. It records or imports a lecture, turns the speech into text on the phone, and then uses an AI service to write study notes from that text. Everything else supports those two jobs.

Features, grouped by what they do

  • Capture. Record in the app (keeps going with the screen off). Record a video with the camera button. Import or share audio and video files, including from other apps' Share menus. Only the audio of a video is kept.
  • Organise. Subjects (courses) with colours, filter chips, lectures grouped by date, multi-select to move or delete, and search across titles, transcript lines, notes and slide text.
  • Transcribe on the phone. The app scans the phone and runs a speed test automatically the first time you open Speech models, then recommends a Whisper model (Tiny, Base, Small, Medium). Phones too limited for any model get a clear explanation instead. Transcription runs in the background in 2-minute chunks, resumes after interruptions, pauses when the phone is hot, and waits while the battery is low.
  • Fix the transcript. Long-press a line to edit it, or use Find and replace across the whole transcript.
  • Speaker labels (optional). Find who is speaking, listen to voice samples, rename, mark the lecturer, and merge speakers who are the same person.
  • Slides and PDFs. Attach PDFs, PowerPoints, photos or text files, or make a lecture from slides alone. Text is extracted on the phone, with OCR for scans.
  • AI notes. Pick a provider (Groq, OpenRouter, Cerebras, Ollama, a custom server, or Claude) with your own key. Choose a style (Brief, Standard, Detailed), an optional length limit, and how many flashcards and quiz questions to get. The notes have sections with timestamps, "going deeper" explanations, key terms, class Q&A, flashcards and a quiz. Each subject can have its own prompt.
  • Study. Pick lectures to study, review flashcards on a spaced-repetition schedule, cram all cards before an exam, and take quizzes with saved scores. Tapping any timestamp plays that moment of the lecture.
  • Export. PDF, Markdown, or an Anki import file.
  • Look after storage. Audio is compressed after transcription (~115 → ~14 MB per hour). Backup & restore puts everything in one zip.

Languages and the toolchain

A toolchain is the set of programs that turns source code into something a device can run. Android apps have two toolchains working side by side: one for Kotlin (which runs on Android's Java-style runtime) and one for C++ (which runs directly on the phone's processor).

The three SDK numbers

  • minSdk = 26 (Android 8.0): the oldest Android the app installs on. Below this, some APIs it uses (like foreground service types and modern media codecs) are missing.
  • targetSdk = 34 (Android 14): the Android version the app is designed and tested for. Android applies that version's rules to the app, for example requiring a declared foreground service type such as microphone.
  • compileSdk = 34: the API level the code is compiled against, which decides which Android functions exist at compile time.

ABIs: which processors the app supports

An ABI (application binary interface) is a CPU family plus its calling rules. Native code must be compiled separately for each ABI. This app builds for arm64-v8a (almost every modern phone) and, in debug builds only, x86_64 (the Android emulator on a PC).

RecapKotlin for the app, C++ for speech recognition, XML for Android's declarations. JDK 17 runs the build. The SDK supplies Android's API, and the NDK plus CMake compile native code for arm64 phones.
Module 3

Gradle in depth

You'll learnWhat Gradle is, how this project's build files fit together, what the build types do, and exactly what happens when you run ./gradlew assembleRelease.

Gradle is a build automation tool. You describe the project (its source folders, dependencies and options) and Gradle works out the tasks needed to produce an app, runs them in the right order, and skips any whose inputs haven't changed. Android support comes from a plugin, the Android Gradle Plugin (AGP), which adds tasks like compiling resources, building native code, shrinking and signing.

The wrapper: a pinned Gradle version

Nobody installs Gradle by hand. The project includes a small launcher, gradlew (or gradlew.bat on Windows), that downloads the exact Gradle version named in gradle/wrapper/gradle-wrapper.properties the first time it runs:

# gradle/wrapper/gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-8.7-bin.zip

The four configuration files

settings.gradle.kts

Read first. Says where to download plugins and libraries from (Google's Maven repository, Maven Central and the Gradle Plugin Portal), names the project LectureNotes, and includes the one module, :app. FAIL_ON_PROJECT_REPOS forces every repository to be declared here and nowhere else.

build.gradle.kts (root)

Declares plugin versions for the whole project without applying them (apply false): AGP 8.5.2, Kotlin Android 1.9.24, and KSP 1.9.24-1.0.20.

app/build.gradle.kts (module)

The real configuration: applies the three plugins, then sets the SDK levels, native build, build types, signing, packaging, Java version, Compose, the Room schema folder and every dependency.

gradle.properties

Build-wide switches: org.gradle.jvmargs=-Xmx3g (3 GB of memory for the build), android.useAndroidX=true (use AndroidX libraries), android.nonTransitiveRClass=true (each module's resource class holds only its own resources, which speeds builds).

The three plugins

  • com.android.application (AGP 8.5.2) turns the module into an Android app: it compiles resources, merges manifests, runs R8, packages and signs APKs.
  • org.jetbrains.kotlin.android (1.9.24) compiles Kotlin for Android.
  • com.google.devtools.ksp (1.9.24-1.0.20) is Kotlin Symbol Processing. It reads annotations at compile time and generates code. Room uses it: you write @Dao interfaces and KSP writes the SQL-calling code for you. Its version must match the Kotlin version, which is why it reads 1.9.24-….

Compose needs a matching compiler

With Kotlin 1.9, Jetpack Compose's compiler is a separate piece pinned to the Kotlin version: composeOptions { kotlinCompilerExtensionVersion = "1.5.14" }. Version 1.5.14 is the one built for Kotlin 1.9.24. A mismatch is a common build failure.

A lesson learned: ABI filters were first set once in defaultConfig, and the release build still contained x86_64. Gradle adds a build type's filters to the default ones instead of replacing them. Moving the filters into each build type fixed it.

Signing

Every APK must be signed. The release key lives outside the repository at ~/.android/lecturenotes-release.jks, a Java keystore (the format keytool makes). Its passwords live in keystore.properties, which git ignores. The build reads that file with java.util.Properties.

If the file is missing (for example on another computer), the release build type still points at the debug key, so Gradle can configure the project and debug builds keep working. But since commit 6b94165, a check stops any build that would actually package a release with it. Module 11 explains why that matters.

// end of app/build.gradle.kts
gradle.taskGraph.whenReady {
    val releaseKey = android.signingConfigs.findByName("release")?.storeFile
    val packagesRelease = allTasks.any { it.project == project && it.name in setOf("packageRelease", "signReleaseBundle") }
    if (packagesRelease && releaseKey?.exists() != true) throw GradleException("Release builds need the release key. …")
}

taskGraph.whenReady runs after Gradle has decided which tasks to run but before any of them start. So assembleRelease and bundleRelease fail straight away, while assembleDebug and assembleReleaseTest, which package with the debug key on purpose, are unaffected.

R8: shrinking and renaming

R8 is the release optimiser. It removes unused code, inlines small functions, and renames classes to short names. That breaks anything that finds code by name at runtime, which here means the native libraries. proguard-rules.pro holds the exceptions:

# app/proguard-rules.pro (what the rules protect)
-keep class com.lecturenotes.whisper.WhisperNative / NativeSegment ...   # C++ builds these by name
-keep class com.k2fsa.sherpa.onnx.** { *; }                              # sherpa's JNI reads fields by name
-dontwarn com.gemalto.jp2.**                                             # PdfBox's optional JPEG-2000 decoder isn't included

Native build and packaging

externalNativeBuild { cmake { path = file("src/main/cpp/CMakeLists.txt"); version = "3.22.1" } } tells AGP to run CMake for each ABI. The default config passes -DANDROID_STL=c++_shared, so the C++ standard library is shipped once as a shared library. packaging { jniLibs { useLegacyPackaging = true } } extracts native libraries to disk at install time instead of loading them straight from the APK. GGML needs that, because it picks and loads the best CPU-variant library file at runtime (Module 5).

Dependencies and the Compose BOM

Dependencies are declared with configurations that say where each library is needed:

  • implementation: compiled into the app.
  • debugImplementation: only in debug builds (Compose's UI inspection tools).
  • ksp: a code generator that runs at compile time (Room's compiler).
  • testImplementation: only for unit tests on the computer.

A BOM (bill of materials) is a list of versions that are known to work together. platform("androidx.compose:compose-bom:2024.06.00") sets the versions of all Compose libraries at once, which is why lines like androidx.compose.material3:material3 have no version number.

Other settings in the module file

  • compileOptions and kotlinOptions target Java 17.
  • buildFeatures { compose = true; buildConfig = true } turns on Compose and the generated BuildConfig class (debug flag, version).
  • ksp { arg("room.schemaLocation", "$projectDir/schemas") } makes Room export a JSON description of each database version into app/schemas/.
  • testOptions { unitTests { isIncludeAndroidResources = true } } lets Robolectric tests see the app's resources.

Module 5

Native code: whisper.cpp, GGML, JNI and sherpa-onnx

You'll learnHow C++ speech recognition runs inside a Kotlin app, why several CPU variants are built, and how the speaker engine is packaged.

whisper.cpp as a git submodule

OpenAI's Whisper is a speech recognition model. whisper.cpp is a C++ re-implementation that runs it efficiently on CPUs. It's included as a git submodule: a separate repository pinned to one commit (tag v1.8.7) inside third_party/whisper.cpp. The app compiles it from source, so the build options can be tuned for phones.

GGML and CPU variants

whisper.cpp does its maths with GGML, a small tensor library. Phone CPUs differ in which fast instructions they support (dot-product, fp16, i8mm, armv9). CMakeLists.txt builds GGML's CPU code once per instruction level, and GGML loads the best one for the phone when the app starts:

# app/src/main/cpp/CMakeLists.txt (abridged)
set(GGML_BACKEND_DL        ON)   # CPU code in separate, loadable libraries
set(GGML_CPU_ALL_VARIANTS  ON)   # one per instruction-set level
set(GGML_NATIVE            OFF)  # don't tune for the build computer's CPU
set(GGML_OPENMP            OFF)
set(WHISPER_BUILD_TESTS/EXAMPLES/SERVER OFF)
add_subdirectory(${WHISPER_DIR} whisper.cpp)
add_library(whisper_jni SHARED whisper_jni.cpp)
target_link_libraries(whisper_jni PRIVATE whisper ggml ggml-base log android)
target_compile_options(whisper_jni PRIVATE -O3 -Wall)

JNI: calling C++ from Kotlin

JNI (Java Native Interface) connects the two worlds. Kotlin declares external funs, and the C++ file implements functions with matching names. These are the app's bridge functions (WhisperNative.kt ↔ whisper_jni.cpp):

Kotlin declarationWhat the C++ side does
nativeLoadBackends(libDir)Loads the GGML backend libraries, choosing the best CPU variant.
nativeSystemInfo()Reports which CPU features were detected.
nativeAllowedCpus()Calls sched_getaffinity to list the cores this thread may run on.
nativeInit(modelPath) / nativeFree(handle)Loads a model file into native memory and returns a handle, or frees it.
nativeTranscribe(handle, samples, threads, initialPrompt, listener)Runs Whisper on a chunk of float samples (greedy decoding, English, non-speech tokens suppressed) and returns an array of segments, calling back with progress.
nativeAbort(handle) / nativeCpuShrunk(handle)Stops a running transcription. The abort callback checks every 500 ms whether the allowed CPUs shrank.

The model lives in native memory that Kotlin's garbage collector doesn't see, so WhisperContext implements Closeable and frees it explicitly. Because R8 would rename the Kotlin classes that C++ looks up by name, they have keep rules (Module 3).

Room tables: recordings, segments, subjects, notes, review_cards, quiz_attempts, attachments, attachment_pages, speakers. The schema grew one feature at a time. Each version has a hand-written migration, SQL that upgrades an existing database without losing data:

Transcription

  • Audio is always 16 kHz mono PCM16 WAV, about 1.9 MB per minute.
  • ChunkPlanner cuts ~2-minute chunks at the quietest half-second near each target. Each chunk is a checkpoint (transcribedMs).
  • For imports, decoding and transcription overlap: the first chunk starts after ~2¾ minutes are decoded (12 s after sharing a 7-minute video, instead of ~40 s).
  • Threads = fast cores among the allowed CPUs. In the background, vivo limits the app to cores {0,1,5,6}. Oversubscribing was 14× slower (408 s vs 30 s per 60 s of audio).
  • Foreground: about 3.5× faster than real time with Small. Background: about real time.
  • No carried-over prompt between chunks: it made Whisper skip repeated speech.
  • A HeavyWork mutex lets only one heavy job run at a time, and Thermal pauses at severe heat.

Model choice: checking what a phone can handle

The app can be installed on any arm64 phone with Android 8.0 or newer, so it can't assume a fast phone like yours. It decides in three steps, all on the phone it's running on.

Step 1: the hardware scan (automatic, every visit)

Opening Settings → Speech models runs DeviceInfo.read(), which collects:

  • Total RAM, from Android's ActivityManager.MemoryInfo.
  • The chip name, from Build.SOC_MANUFACTURER and Build.SOC_MODEL on Android 12+, or Build.HARDWARE on older phones.
  • Cores and fast cores. It reads each core's top clock speed from /sys/devices/system/cpu/cpuN/cpufreq/cpuinfo_max_freq, and every core faster than the slowest group counts as fast.
  • Free storage, from StatFs on the app's folder.

A model fits when the phone's RAM (plus 0.5 GB, because phones report a bit less than advertised) meets the model's minimum. To download it, free storage must also be more than twice its size; storage stops mattering once it's downloaded. Models that don't fit are blocked: the Download button is disabled with the reason, and a downloaded model too big for the phone's memory can't be selected or used.

The RAM minimums come from measured peak memory while transcribing a 30-second clip: whisper.cpp alone uses Tiny 104 MB, Base 176 MB, Small 369 MB, Medium 843 MB, and the app adds about 80 MB. On your phone the app peaked at 181 MB during the Tiny test. Android kills large apps well before RAM is full, so each minimum leaves at least 6× the model's peak as headroom.

Step 2: the speed test (automatic on the first visit)

DeviceCheck.run() downloads Tiny if needed (32 MB), transcribes the bundled 30-second clip assets/bench30.wav once to warm up and once timed, and reads whisper.cpp's encode time. Then, for every model:

minutes per lecture hour = Tiny encode time × (encode ratio + decode ratio) × 120 windows of 30 s

Decoding is estimated from encode ratios because the short test clip decodes unrealistically fast. On your phone this predicts Small at ≈ 15 minutes per hour, against ≈ 17 measured.

The test starts by itself the first time Speech models is opened, once per install. A failed test isn't retried automatically, but leaving the screen mid-test lets it try again next visit, and "Test again" re-runs it any time. Results are stored in the phone's own models settings, which backups leave out, so a new phone always measures itself.

Step 3: the recommendation

  • With a speed test: the most accurate model that fits and does a 1-hour lecture in 20 minutes or less with the app open. If none is that fast, it picks the fastest model that fits and warns: "This phone is slow for transcription: even Tiny takes about N min per lecture hour."
  • Without one: a memory-only guess, the biggest model that fits but never Medium. The screen says the recommendation is based on memory only.
  • When nothing fits: no recommendation at all. The screen says "This phone can't transcribe on-device" and explains why: "needs at least 2 GB of RAM, and this phone has X GB", or "free up at least N MB". It adds that notes from slides and PDFs still work, because those don't need Whisper.
What the checks can't know: the speed ratios between models were measured on one chip (Snapdragon 8s Gen 4), so estimates on other chips are approximate. Estimates also assume the app is open; some brands, like vivo and Xiaomi, slow background apps 2–3×. A phone that is 32-bit only or older than Android 8.0 can't install the app at all, so it never reaches these checks.

Model downloads come from Hugging Face, resume if interrupted, and are verified by SHA-256 before use.

Speakers

  • Models: pyannote segmentation 3.0 (int8, 1.5 MB) finds turns; 3D-Speaker CAM++ (30 MB) makes voice embeddings. Downloaded on first use.
  • Processed in 10-minute pieces: 80 minutes of float audio would be ~300 MB in memory.
  • Clustering threshold 0.9 instead of sherpa's default 0.5, which turned the lecturer into 15 speakers.
  • SpeakerLinker links pieces by cosine similarity to running-average centroids, gives each line the speaker with most overlap, and drops voices under 3 s.
  • About 13 minutes for an 80-minute lecture with the app open. The phone reached thermal status 4.
  • Merging moves lines, combines talk time, and renumbers default names in one transaction.

Slides

  • PDF text layer via PdfBox. Pages with fewer than 20 characters are treated as scans: rendered with PdfRenderer and read with ML Kit OCR.
  • PPTX files are zip archives of XML: the app reads the <a:t> text runs of each slideN.xml plus speaker notes from notesSlideN.xml.
  • Text files are split into ~250-word pages. Slides are numbered 1..n across all of a lecture's files.
  • SlidePicker sends the most relevant slides with each transcript part (TF-IDF word overlap, up to ~700 tokens).

Notes generation

  • Input: one [mm:ss] text line per segment, so every note can cite its moment. Speaker tags appear where the speaker changes, and the lecturer is always tagged as such.
  • One request if the lecture fits, otherwise parts of up to ~4k tokens (about 15 minutes of speech), merged in code, plus one small request for the title and overview.
  • Learns the provider's real limit from 413 "Limit X, Requested Y" errors, paces from x-ratelimit-* headers, waits for retry-after on 429, splits a part if the reply is cut off, and saves finished parts in partialJson.
  • Broken JSON: repair, then retry with a reminder, then retry without JSON mode (3 attempts).
  • Length budget: Brief, Standard and Detailed = 10%, 20% and 35% of transcript words (50%, 100% and 150% of slide text for slides-only lectures, minimum 150). Enforced if more than 25% over.
  • Flashcards 0–60 and quiz 0–30, or Auto, which scales with length.
  • A real run: 2,010 words against a 2,229-word budget, 28 cards, 15 quiz questions.

Study (SM-2)

  • New card buttons: Again 1 min, Hard 6 min, Good 1 day, Easy 4 days.
  • After that, intervals grow by the card's ease factor (minimum 1.3), capped at 365 days.
  • 20 new cards a day. Cards due within 20 minutes come back in the same session.
  • Cram mode shows every card shuffled without changing the schedule. Regenerating notes keeps the schedule of unchanged questions.

Storage and backup

  • After transcription: AAC 32 kbps in .m4a (~14 MB per hour), duration-checked (within 2 s) before the WAV is deleted.
  • Backup zip: manifest.json (format, DB version, original folder, settings), database/lecturenotes.db (after a WAL checkpoint), files/audio/…, files/attachments/….
  • Restore: stage, validate, rewrite paths, swap by rename, roll back on failure, restart. Your real backup was 133 MB for 3 lectures.

Module 11

Releasing

You'll learnWhy debug and release are different apps to Android, how your phone was switched without losing data, and how the app was published with a website anyone can download it from.

Android remembers which key signed an installed app and accepts updates only with the same key. The debug build was signed with Android Studio's automatic debug key, and the release build with your release key. That makes them incompatible as updates, even though both use the ID com.lecturenotes. Uninstalling deletes the app's data, which is why Backup & restore was built first.

The switch, step by step

  1. Built the release APK and verified its signature with apksigner.
  2. Made a fresh backup in the app (Settings → Back up) and checked it on the computer: integrity ok, 3 lectures, 991 lines, notes, 28 cards.
  3. Saved two safety copies in ~/LectureNotes-backups/: the backup zip and a raw tar of the app's data folder.
  4. adb uninstall com.lecturenotes, then adb install app-release.apk. The installed app no longer had the DEBUGGABLE flag.
  5. Settings → Restore → picked the zip → "Replace and restore". The app restarted with everything back.
  6. Left for you: entering the Groq key again (keys never travel) and downloading the Small speech model.

Updating from now on

./gradlew :app:assembleRelease
adb install -r app/build/outputs/apk/release/app-release.apk   # keeps all data

This only works while you still have lecturenotes-release.jks and keystore.properties. Keep copies somewhere other than this computer.

Publishing: repository, website and download

On 27 October the project went public, in three pieces that all live on GitHub:

  • The repository, github.com/Dasa108/lecture-notes, holds the source and full history. Before making it public, the whole history was searched for the release key, keystore.properties and API keys. None had ever been committed, thanks to .gitignore.
  • A GitHub Release (tag v0.1.0) carries the signed APK as an attached file named LectureNotes.apk. Release files sit outside git history, so the 28.5 MB APK doesn't make every clone bigger.
  • GitHub Pages serves the website from the docs/ folder on main at dasa108.github.io/lecture-notes. It's one hand-written HTML file with no build step. An empty docs/.nojekyll file turns off Jekyll, the site builder Pages would otherwise run.

The site's Download button links to releases/latest/download/LectureNotes.apk. GitHub redirects that address to the file in the newest release, so the page never needs editing when you ship an update.

The commands used, with the gh GitHub command-line tool:

gh repo create Dasa108/lecture-notes --public --source . --remote origin --push
gh release create v0.1.0 LectureNotes.apk --title "Lecture Notes 0.1.0"
gh api -X POST repos/Dasa108/lecture-notes/pages \
  -f "source[branch]=main" -f "source[path]=/docs"   # turn on Pages

To ship version 0.2.0: raise versionCode and versionName in app/build.gradle.kts, run assembleRelease, copy the APK to LectureNotes.apk (the name must stay the same), and run gh release create v0.2.0 LectureNotes.apk. Because it's signed with the same key, people install it over the old version and keep their lectures.

Keys and signing, in depth

Signing is how Android knows who made an app. A signature proves two things: the APK hasn't been changed since it was signed, and every version came from the same developer. Android uses the second to decide whether an update may replace an installed app.

PieceIn this project
Keystore~/.android/lecturenotes-release.jks, a password-protected file that holds one or more keys. Made once with keytool -genkeypair.
Key (alias)An RSA 4096-bit private key with a self-signed certificate, CN=Lecture Notes, O=Personal. The alias is the key's name inside the keystore.
Two passwordsThe store password opens the keystore; the key password unlocks the key. Both sit in keystore.properties, never in git.
Certificate fingerprintThe SHA-256 of the certificate: 87509efe…037277. Every genuine Lecture Notes APK shows this exact value.
Signature schemeAPK Signature Scheme v2, which signs the whole file. The old v1 (JAR) scheme is skipped because minSdk 26 doesn't need it; v1 only matters below Android 7.0.

Why the key can never change. Android compares the new APK's certificate with the installed app's. If they differ, the install fails with INSTALL_FAILED_UPDATE_INCOMPATIBLE and the only way forward is uninstalling, which deletes every lecture. That's why a release accidentally signed with the debug key would be so bad, and why the build now refuses to make one.

Checking a signature:

apksigner verify --print-certs app-release.apk   # shows the DN and SHA-256 fingerprint

The backup. If the key is lost, no update can ever reach people who installed the app. If it's stolen, someone could sign a fake update that installs over yours. So the backup is encrypted: the keystore and keystore.properties are packed with tar and encrypted with gpg --symmetric (AES-256) using a passphrase only you know, into ~/LectureNotes-backups/lecturenotes-release-key.tar.gz.gpg. A README next to it explains how to restore it. One copy must live somewhere other than this computer.

gpg -d lecturenotes-release-key.tar.gz.gpg | tar -xz -C ~   # restore on a new computer

What the Play Store would change. With Play App Signing, Google keeps the key that signs what users install, and you only hold an upload key, which can be reset if lost. Installing APKs directly from GitHub has no such safety net, so your own backup is the only protection.

The page also shows the APK's SHA-256 checksum, so anyone can confirm the file they downloaded is the one you published. Its layout was checked by taking full-page screenshots with headless Firefox at desktop width (1280 px) and phone width (390 px).

Future updates install over it with adb install -r, as long as the key is kept. The public download is an APK on a GitHub Release, linked from a GitHub Pages site in docs/.
