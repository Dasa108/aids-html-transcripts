Module 00

Start here

The one-minute answer, the numbers to remember, and how to talk about how it was built.

Your 60-second answer to "Tell me about your project"

In the interview

"I built xG Match Companion, a mobile website for logging shots during a local football match. You tap where each shot happened on a drawing of the pitch, and a machine-learning model running inside the phone's browser gives the shot's expected goals: the chance that kind of shot becomes a goal. At full time it produces a report showing which team created the better chances, a player leaderboard, charts and downloadable exports.

I trained the model in Python with LightGBM on 34,809 real shots from StatsBomb's open data, calibrated it so its percentages can be trusted, and exported it to ONNX so it runs in the browser. The front end is React with TypeScript, built with Vite. All data stays on the phone in IndexedDB, and a service worker makes the whole app work offline. There is no server. It's hosted on GitHub Pages, deployed automatically by GitHub Actions, and covered by 593 automated tests."

Module 01

What xG means

The football idea behind the whole project.

xG stands for expected goals. It is a number between 0 and 1 for every shot: how often a shot like that ends up as a goal.

  • A tap-in from 2 metres in front of an empty goal might be 0.8. Eight out of ten go in.
  • A shot from just inside the penalty box, straight on, might be around 0.1–0.3.
  • A hopeful strike from 35 metres might be 0.02. Two in a hundred go in.

Add up all of a team's shots and you get the team's xG for the match. That tells you how many goals they "should" have scored from the chances they made.

In plain words

The scoreline can lie. Team A can win 1–0 with one lucky long shot (0.04 xG) while Team B created 2.3 xG of chances and missed them all. xG shows who actually played better. The app's report says exactly this in one sentence at full time.

Two kinds of xG in this project

Pre-shot xG
How good the chance was before the ball was struck: where, which foot, defenders in the way, the keeper's position. This is the main model, and every shot gets it.
Post-shot xG (PSxG)
How good the finish was, judged by where the ball went in the goal frame. A shot into the top corner is harder to save than one at the keeper. It's optional, only for shots that were on target, and you add it by tapping a drawing of the goal.

Who uses the app

One person on the sideline of a local match, with one phone, logging one match at a time. Often there is no mobile signal. That single fact shaped almost every technical decision in the project.

In the interview

"xG is the probability that a given shot becomes a goal, learned from thousands of past shots. Summed over a match, it shows which team created the better chances, whatever the scoreline says."

Module 02

Websites from zero

The basic building blocks, each one shown in your own project.

A website is just a set of files. Your phone's browser downloads them and runs them. Three languages do almost all the work:

PieceIts jobHouse analogyIn your project
HTMLStructure: headings, buttons, listsThe walls and roomsapp/index.html, plus what React produces
CSSLooks: colours, fonts, spacing, animationPaint and furnitureapp/src/styles.css
JavaScriptBehaviour: what happens when you tapElectricity and plumbingEverything in app/src/, written as TypeScript

The tools on top of those three

TypeScript
JavaScript with labels saying what kind of data each thing holds ("this is a number", "this is a Match"). The computer checks the labels before the code runs, so many mistakes are caught early. In this project, adding two new fields to Match made TypeScript flag three test files that had not been updated.
React
A way to build a page out of small reusable pieces called components, like Lego bricks. Pitch draws the pitch, ShotEntry is the shot form, Charts draws the graphs. When data changes (called state), React redraws only the parts that need it.
Vite
The build tool. While you work, it runs a local preview server (npm run dev). For release, it packs and shrinks all the code into a few small files (npm run build). Think of it as the kitchen that turns raw ingredients into a plated meal.
Node and npm
Node runs JavaScript on your computer rather than in a browser. npm downloads the libraries the project uses (React, Dexie and so on). package.json lists them. This project uses Node 24.
SVG
A picture made of shapes and coordinates rather than pixels, so it stays sharp at any size. The pitch, the goal frame, all charts and all icons in this app are SVG drawn in code. No charting library is used.
Mobile-first
Design for a phone screen first, then let it stretch for bigger screens. The user here is always on a phone on a sideline.
Frontend / backend
The frontend is what runs on your device. A backend is a server somewhere else that stores data or does work. This project has no backend. It is a static site: just files that get downloaded.
localStorage
A tiny notepad inside the browser for small settings. Used here to remember the last open match and the offline-mode setting.
IndexedDB
A real database inside the browser. Every match, player and shot is saved here, on the phone only. The project uses a library called Dexie to make it easier to use.
Service worker
A small background script that saves a copy of the whole site onto the phone, so it keeps working with no internet. Like downloading an offline map before a hike.
PWA
Progressive Web App: a website that behaves like an installed app (works offline, can update itself). The service worker is what makes this one a PWA.
WebAssembly (wasm)
A way to run fast, pre-compiled code inside the browser. The model is run by a library called onnxruntime-web, which uses wasm under the hood.
Likely follow-up

"Why React and not plain HTML?" The app has many pieces that change on every tap (markers on the pitch, live xG, the clock, tallies). React keeps the screen in sync with the data automatically, and splits the UI into components that are easy to reuse. For example, the same pitch markings are drawn on the shot-entry screen and on the report's shot map.

Module 04

Planning first

How the work was organised before and during the build.

Before any code, a specification (spec.md) answered: what exactly does the sideline person tap, what does the model need to know, and what score counts as "good enough to ship". When reality disagreed with the plan, the plan was updated on purpose, so it never went stale.

Every step was also logged in process.md as a learning journal: what was done, why, how, and what went wrong.

The four milestones

Decisions locked early

  • One adaptive model instead of separate "quick" and "detailed" modes.

Module 05

Data and features

What the model learns from, and the clues it looks at.

The data

StatsBomb Open Data is free, real, shot-by-shot data from professional football, released for non-commercial use. The project used 34,809 shots from 1,374 matches across 13 competitions (Premier League, World Cups, Euros, women's leagues and more). A mix of competitions was used on purpose, so the model learns "what makes a good chance" rather than "this one team is good".

A key reason for choosing StatsBomb: each shot has a freeze frame, a snapshot of where every visible player was at the moment of the shot. That lines up with the keeper and defender markers the operator drops on the pitch.

Positions use StatsBomb's pitch units: 120 × 80, with the goal at x = 120 between y = 36 and y = 44. These are not metres.

Features: the clues

A feature is one number or category the model uses to guess. The two strongest by far are distance and angle.

Features are organised into groups. Only the core group is always available. The others depend on how much the operator had time to enter.

GroupFeatures (code names)Comes from
coredistance, angle, dist_x, abs_y, in_box, in_six_yard, body_part, shot_type, play_pattern, under_pressureThe shot tap + quick chips
freeze_framedefenders_in_cone, nearest_def_dist, def_within_3/5, gk_dist, gk_dist_from_goal, gk_lateral, gk_in_cone, teammates_in_boxKeeper and defender markers
assistassist_type"+ more detail"
techniquetechnique (volley, lob, header…)"+ more detail"
contextfirst_time, follows_dribble, one_on_one, open_goal, rebound"+ more detail"
pass_originpass_origin_dist, angle_swingThe "pass" tool on the pitch

"In the cone" means inside the triangle between the ball and the two posts, the shaded wedge in the picture. A defender in the cone is in the way of the shot.

Why penalties are a fixed 0.76

Penalties are almost the same every time (same spot, only the keeper), and their real-world scoring rate is well known. So they skip the model and always get 0.76. This is a documented exception, not a shortcut.

Likely follow-up

"What is feature engineering?" Turning raw facts (x and y of a tap, marker positions) into clues a model can use (distance, angle, how many defenders block the view). The same feature maths exists twice: in Python for training and TypeScript in the app. Module 08 explains how they're kept identical.

Module 06

The model

LightGBM, explained without maths, plus the trick that lets it cope with missing information.

From one decision tree to LightGBM

  1. A decision tree is a flowchart of yes/no questions. "Is the shot inside the box? Yes. Is it from a header? No. Is a defender in the cone? No." At the end you get a guess.
  2. One tree is crude. Gradient boosting builds many small trees one after another. Each new tree focuses on the mistakes the trees before it made, like a team of students where each one corrects the previous person's homework.
  3. LightGBM is a popular, fast library that does gradient boosting. It's strong on table-shaped data like this.

It is a binary classifier: the answer is goal (1) or no goal (0), and it outputs a probability between them. That probability is the xG.

Key settings, in plain words

SettingValueMeaning
learning_rate0.02Each tree only nudges the answer a little, so learning is slow and careful
n_estimators + early stopping≤ 4000, stop after 120 with no gainKeep adding trees until the validation score stops improving
max_depth / num_leaves5 / 31Keeps each tree small so it can't memorise
min_child_samples60A rule needs at least 60 shots behind it
subsample / colsample0.8 / 0.8Each tree sees a random 80% of shots and features, which adds variety
monotone_constraintsonCommon-sense rules (below)

Monotone constraints: built-in common sense

The model is forced to obey football logic, even if the data is noisy: further away can never raise xG, a wider angle can never lower it, more defenders in the cone can never raise it, and a one-on-one or open goal can never lower it. This stops strange predictions.

The baseline: the bar to beat

Before trusting LightGBM, a simple logistic regression using only geometry (distance and angle) was trained. If the fancy model can't beat that, it isn't worth shipping. Baseline test log loss was 0.274. LightGBM got 0.263.

One model that copes with missing inputs

On a real sideline you may only have time to tap where the shot was. Other times you mark the keeper, the defenders and more. Rather than build a "quick mode" and a "detailed mode", the project trained one model that handles both, by practising with missing information.

Each real training shot was copied five times:

  1. Once with everything filled in.
  2. Once with only the core features (all optional groups blanked).
  3. Three more times with random groups blanked, and marker positions slightly shifted (jitter) to imitate a rushed thumb tap being about 1.5 m off.

This is called feature-group dropout and data augmentation. Every entry is then labelled with a completeness bucket:

BucketWhat was entered
minimalOnly the core: shot spot, body part, situation, pressure
partialCore + keeper/defender markers
fullEverything, including assist, technique, pass origin and context
In plain words

Like a doctor who still gives a sensible diagnosis with whichever test results are back, instead of refusing to guess until every test is in.

In the interview

"It's a LightGBM gradient-boosted tree model with monotone constraints, so it can't learn things like 'further away is better'. I trained one model on augmented data where optional feature groups were randomly dropped, so it works whether the operator enters two things or twenty."

Module 07

Testing the model honestly

How the data was split, why calibration matters, and what each score means.

Hide some data, and hide it by match

If you test a model on the shots it learned from, it looks perfect, because it's remembering answers. So shots are split into separate piles: train (learn), validation (decide when to stop), calibration (tune the percentages) and test (the final exam, 15%: 4,988 shots from 197 matches).

The split is by match, not by shot. Two shots from the same game share teams, weather and referee, so if one is in training and one in the test, the test is too easy. A match's ID is put through a fixed hash function to decide its pile, so the split is the same every time.

A real mistake, and the lesson

The first attempt held out whole tournaments for testing. Those tournaments happened to have a different mix of easy and hard chances, so the model's percentages came out slightly off, even though it ranked chances well. Switching to holding out individual matches from every competition fixed it. The lesson: "is it accurate" and "is it calibrated" are two different questions.

Calibration: making percentages trustworthy

If the model says 0.30 for a hundred shots, about 30 of them should be goals. A model can rank chances correctly and still have wrong percentages.

In plain words

A weather forecaster who says "70% rain" but it only rains 20% of those days is badly calibrated, even if rainy days do get higher numbers.

The fix is isotonic regression: a correction table, learned on held-out data, that maps the raw score to a trustworthy probability. It only ever moves numbers up or down in order, never swapping two shots' ranking. A separate table was fitted for each completeness bucket, because guesses made with little information go wrong in different ways from guesses made with full information. The tables ship as calibrators.json.

The scores, explained

Log loss
Punishes confident wrong guesses heavily. Lower is better. Main score here: 0.263.
Brier score
The average squared gap between the predicted probability and what happened (0 or 1). Lower is better: 0.071.
AUC
If you pick one goal and one miss at random, how often does the goal have the higher xG? 0.5 is coin-flipping, 1.0 is perfect. Here: 0.805.
ECE
Expected calibration error: how far the percentages are from reality, on average. Lower is better: 0.013.
Calibration-in-the-large
Total predicted goals ÷ actual goals. 1.03 means it predicted 3% more goals than happened, very close to perfect.
Correlation with StatsBomb xG
How closely it agrees with the professional provider's own xG: 0.90.

Quality drops gently as less is entered, which is exactly what you want. Every bucket beats the baseline.

The release gate

Pass/fail thresholds were written into the spec before training (section 8.6). The model only shipped once every bucket passed every check. Gate result: PASS. Full numbers are in models/metrics.md.

In the interview

"I split by match to prevent leakage, set pass/fail thresholds before training, and calibrated with isotonic regression per completeness level. On 4,988 unseen shots it got AUC 0.805 and log loss 0.263, beat the geometry baseline at every level, and correlated 0.90 with StatsBomb's own xG."

Module 08

Getting the model into the browser

ONNX, onnxruntime-web, and the "answer key" that keeps two languages in agreement.

ONNX

The model was trained in Python, but browsers run JavaScript. ONNX is a standard file format for trained models. Python saves the model as model.onnx (422 KB), and onnxruntime-web loads and runs it inside the browser using WebAssembly.

In plain words

Like saving a Word document as a PDF. It isn't a Word file any more, but any PDF reader on any computer shows exactly the same thing.

The export was checked: the ONNX version gives the same answer as the Python model to seven decimal places.

Two copies of the same maths, kept honest

The feature maths (distance, angle, defenders in the cone…) exists twice: in Python (training/features.py) and in TypeScript (app/src/xg/features.ts). If they ever drifted apart, the app would quietly give wrong xG and nobody would notice.

The fix is a shared answer key: 48 real shots were run through the Python code, and the exact outputs were saved to feature_fixtures.json. The app's tests run the same shots through the TypeScript code and fail loudly if any number differs beyond tiny rounding. These are called parity tests (340 of them at first). The same approach was reused for the PSxG model.

Making it fast enough on a phone

  • Lazy loading: the model library is only downloaded when you open the live screen, not on the first page. The main bundle shrank from 694 KB to 277 KB.
  • Smaller wasm: importing the wasm-only build of onnxruntime-web cut the wasm file from 28 MB to 14 MB.
  • Single thread: the multi-threaded mode needs special server security headers that GitHub Pages doesn't send, and it froze the page. One thread is plenty for one small model.
In the interview

"I exported the LightGBM model to ONNX and run it with onnxruntime-web, so inference is on the device. Because the feature code exists in both Python and TypeScript, I built parity tests from a shared fixture file, so any drift between the two fails the build."

Module 09

The app screens

What the user sees, in order, and what happens behind each tap.

Match listpick or create a match
→
Setupteams, players, half length
→
Liveclock + shot logging
→
Reportverdict, charts, export

How the app decides which screen to show

Each match has a status: setup → live → finished. The screen shown simply follows the status stored in the database. Press "Kick off" and the status becomes live, so the Live screen appears. This is a state machine: a fixed set of states with clear moves between them.

Logging one shot

  1. Choose a tool: shot, keeper, defender (up to 6) or pass. Then tap the pitch to place it.
  2. Pick the team and the shooter from the team sheet.
  3. Quick chips with sensible defaults: body part, situation (open play, corner, penalty…), pressure.
  4. Optional "+ more detail": technique, beat a defender, open goal, rebound.
  5. Choose the outcome: goal, saved, off target, blocked, post.

Only the shot spot, the shooter and the outcome are required. The live xG updates instantly as you change anything, with a one-line reason ("close range, tight angle") and a confidence band. Mis-placed a defender? Tap it to remove it, or press undo to remove the last one.

Turning a tap into pitch coordinates is simple proportion: where you tapped inside the drawing, as a fraction of its width and height, mapped onto the 120 × 80 pitch (pitch/Pitch.tsx, pitch/geometry.ts).

Be precise about this

The one-line reason is a rule-of-thumb reading of the inputs, not the model explaining itself. True model explanations need a technique like SHAP, which this project deliberately didn't claim to have. Saying this clearly in a viva shows maturity.

The match clock

The clock stores two things: when it was last started, and how much time had built up before that. Elapsed time = saved time + (now − start), if it's running. Halftime is just a pause. Past the half length it shows broadcast style, like 45+3'. A "2nd half →" button switches the half. Pressing "Full time" early shows a warning and asks you to confirm.

Where the data lives

Three tables in IndexedDB via Dexie: matches, players and shots. Deleting a match also deletes its players and shots (a cascading delete), after asking for confirmation. Nothing leaves the phone.

In the interview

"Screens are driven by a match state machine stored in IndexedDB. Logging a shot needs only three required inputs; everything else has a default, so a shot can be logged in about five seconds or in full detail if there's time."

Module 10

The full-time report

The verdict sentence, the leaderboard, the charts, and three export formats.

The verdict rules

Team xG is the sum of its shots' xG. The difference between the two teams picks the sentence:

SituationSentence
xG gap under 0.3"Even game on chances."
Higher-xG team also won"Deserved result."
Losing team led xG by 0.75 or more"Smash-and-grab / unlucky loss for {team}."
Draw, but xG gap 0.75 or more"{team} will feel they should have won."

Player leaderboard

Per player: shots, total xG, xG per shot, biggest chance, goals, and goals − xG (positive = finished better than expected). Two awards: best xG (most total xG) and most efficient (highest xG per shot, minimum 3 shots, so one lucky shot doesn't win).

Charts, all hand-drawn SVG

  • Shot map: each shot on the pitch, bigger circle for higher xG, shape and colour by outcome.
  • Cumulative xG timeline: each team's xG building up minute by minute, as a step chart.
  • Chance-quality histogram: how many shots were poor, decent or great chances.

The calculations (verdict.ts, report.ts) are kept completely separate from the drawing. Maths is easy to test automatically. Drawing mostly needs a human to look at it. Keeping them apart means a visual tweak can't silently break a number.

Exports, no server needed

  • Full report: one self-contained HTML file with score, verdict, charts, tables and every shot. It opens offline and prints or saves as PDF cleanly.
  • JSON: the same data, machine-readable.
  • CSV: one row per shot, for spreadsheets.

PSxG: the optional second model

For goals, saves and post hits, you can tap where the ball went on a goal-frame drawing. A second model, trained the same rigorous way on 12,423 on-target shots, rates how good the placement was. It uses features such as distance from the nearest post, height, and far post vs near post. Its test log loss was 0.372 against a baseline of 0.507, and AUC 0.879 against 0.772. PSxG is shown alongside xG but never changes the verdict sentence.

In the interview

"The report logic is pure functions with unit tests: team xG, a rule-based verdict, and a player leaderboard. Charts are hand-drawn SVG with no chart library. You can export a self-contained HTML report, JSON or CSV, all generated on the phone."

Module 11

Visual design

The "sports broadcast" look, and how design choices were checked instead of guessed.

Design tokens

All colours, corner radii and timings are defined once at the top of styles.css as CSS variables (also called design tokens), and everything else refers to them. Change one variable and every button using it updates.

:root {
  --bg: #0a0f0c;      /* page background */
  --home: #1fae66;    /* home team green */
  --away: #2c86d1;    /* away team blue */
  --pos: #bd8a12;     /* good / goal gold */
  --neg: #e2465c;     /* bad red */
}
.button { background: var(--home); }

Three separate colour jobs

Originally one green meant "brand", "home team" and "success" all at once, which was confusing. The redesign split colours into three roles that never clash: team identity (home green, away blue), value judgement (good gold, bad red) and shot outcome (goal, saved, post, blocked, off target).

Colour-blind safety, checked by calculation

About 1 in 12 men have some colour blindness. So every outcome has its own shape as well as a colour: ★ goal, ● saved, ◆ post, ▲ blocked, ○ off target. The palette was also run through a validator using OKLab, a model of how humans see colour. It found a real problem: the violet "post" and blue "saved" looked almost identical to people with red-green colour blindness. Post was changed to magenta.

Other design details

  • Tabular numerals: all digits the same width, so the score and xG don't jiggle as they change.
  • Hand-made icon set: no emoji or icon font, so nothing needs downloading and it works offline. The first icons were thin outlines that looked like scribbles at small size. They were redrawn as solid shapes.
  • Motion: screens fade in, the live xG number "pops" when it changes, and a confetti burst plays on a goal. All done with CSS, no animation library.
  • Background art: faint grain texture, pitch-line watermark, soft team-coloured glows, and an original anime-style illustration of a ball bursting through a splash.
A design story worth telling

A stock photo was first used as the background. Before making the repo public, its licence was checked and it turned out to be copyrighted, so it was replaced with original vector art drawn in code. Player silhouettes were also tried twice, didn't look right to the owner, and were removed. Good design includes removing things that don't work.

In the interview

"I used design tokens so colours are defined once, split colour into three roles so meanings never collide, and made outcomes colour-blind safe with shapes plus a palette checked by an OKLab-based validator. That check caught a real collision I wouldn't have seen by eye."

Module 12

Offline, deployment and updates

How the site gets onto the internet, onto the phone, and stays up to date.

Working offline

The service worker is built with Workbox (through vite-plugin-pwa). On first visit it precaches the app, both ONNX models, the calibration files and the wasm runtime, about 14 MB in total. After that, logging, predictions, reports and exports all work in airplane mode.

Hosting: GitHub Pages + GitHub Actions

GitHub Pages hosts static sites for free. A GitHub Actions workflow (.github/workflows/deploy-pages.yml) is a small robot. On every push it installs packages, runs the build, and publishes app/dist. This is CI/CD: continuous integration and deployment. It runs on Node 24, after Node 20 was deprecated.

The blank-page bug

GitHub Pages serves the site from a sub-folder: /xg-match-companion/. Vite has a base setting for this. At first it was switched on for every build, so the local preview asked for files at a path that didn't exist and showed a blank page with no error. The fix: only use the sub-folder when an environment variable GH_PAGES is set, which only the CI robot does.

Updating people who already have it

Once the site is cached on someone's phone, how do they get a new version? Two approaches were tried:

  1. A banner saying "A new version is ready" with a Reload button.
  2. Kept: update automatically as soon as a new version is found, with no button.

With auto-update, the app can only be out of date while offline. So it shows a quiet note: "Offline — may not be the latest version." There's also a toggle to turn offline caching off for anyone who always wants the freshest version.

In the interview

"It's a static PWA on GitHub Pages, deployed by a GitHub Actions workflow. A Workbox service worker precaches everything, including the models, so it works fully offline. It auto-updates when online and honestly flags when it's offline and might be stale."

Bugs and lessons

Real problems from this build. These are your answers to "Tell me about a challenge you faced".

The app has 593 automated tests run by Vitest: feature parity, verdict logic, database lifecycle (using a fake in-memory IndexedDB), report HTML and more. They all passed, yet several serious bugs only showed up by opening the real app in a browser.

The app never started

Problem
All tests green, but the page was blank in a real browser.
Cause
The model library was told to load its files from the public/ folder, which Vite refuses to import code from.
Fix
Let the bundler find the library's files itself.

The page froze on the live screen

Problem
Opening the live screen froze the whole tab.
Cause
onnxruntime-web defaults to multi-threaded wasm, which needs SharedArrayBuffer and special security headers (COOP/COEP) the site doesn't send.
Fix
Force one thread, and load the library lazily with a dynamic import() only when needed.

Blank local preview

Problem
After setting up GitHub Pages, the local preview showed nothing, with no error.
Cause
The Pages sub-folder path was applied to local builds too.
Fix
Apply it only when the GH_PAGES variable is set in CI.

Old version kept showing

Problem
After a rebuild, the browser still showed old code.
Cause
The service worker was doing its job: serving the cached copy.
Fix
During testing, unregister it and clear caches. For real users, it led to the auto-update design.

Hidden colour clash

Problem
Two outcome colours were indistinguishable for colour-blind users.
Cause
Violet and blue collapse together under red-green colour blindness.

Found by an OKLab validator, fixed by shifting to magenta, and shapes added to every outcome.

No way back to the home page

Problem
The owner said that after the report there was no clear way back to the match list.

"My biggest lesson was that unit tests and real-browser testing catch different kinds of bugs. Module 14

Algorithm experiment

Did bagging, XGBoost or a random forest beat the shipped model?

The question came up: "Did we try bagging or boosting, since we used XGBoost?" First, a correction: the model is LightGBM, not XGBoost. Both are gradient boosting libraries, and LightGBM already uses random sampling of rows and features.

Boosting
Trees built one after another, each fixing the last one's mistakes (LightGBM, XGBoost).
Bagging
Many models trained on random resamples of the data, then averaged. Reduces randomness.
Random forest
Bagging applied to many deep, independent decision trees.

A separate experiment script compared all of them on the same test set: the shipped LightGBM, a tuned LightGBM, an average of 5 random seeds, 5 bagged copies, XGBoost and a random forest. Differences were checked with a bootstrap over matches, which tests whether a gap is real or just luck.

Result

  • Nothing clearly beat the shipped model. Bagging added nothing.
  • The random forest was 38 times bigger and scored worse.
  • A tuned LightGBM (smaller trees) was slightly better, by 0.003 log loss, and only with full inputs. That is the same size as the normal variation from changing the random seed, so it wasn't worth rebuilding the shipped model.
In the interview

"I benchmarked bagging, XGBoost and a random forest against the shipped LightGBM with a paired bootstrap over test matches. None clearly won. The only real gain was 0.003 log loss from tuning, within seed noise, so I kept the shipped model and documented the tuned settings for the next retrain."

Module 15

Limits and next steps

Interviewers almost always ask "what would you improve?" Knowing your weak spots is a strength.

  • Pro data, local matches. The model learned from professional football but is used at local matches, where players and keepers differ. This is called domain shift. Retraining on locally logged shots would fix it, but needs a server to collect data from many users.
  • No real match trial yet. Everything was tested in the browser, but not across a full live match on a sideline.
  • Counter-attack tagging hasn't been tested with a real operator under time pressure.
  • Pitch size. Local pitches vary in size. Calibrating to the real pitch was planned but not built.
  • Explanations are rules of thumb, not true model explanations like SHAP. The confidence band widths are illustrative.
  • One device only. No accounts or sync between phones. That would need a backend.
  • Licence. StatsBomb Open Data is for non-commercial use, so the project can't be sold as-is.
In the interview

"The biggest limitation is domain shift: it's trained on professional matches but used at local ones. The next step would be a real pitchside trial, then optional sync so logged local shots could be used to retrain the model."

The project

What problem does your project solve?

Scorelines don't show who created better chances. At local matches there's no data provider, so the app lets one person on the sideline log shots and get instant xG for each, then a full-time report on which team and player created the best chances.

Who is the user and how did that shape the design?

One operator, one phone, one match, often with no signal. That led to: everything running on the phone, offline support, only three required inputs per shot, and one model that works with however much was entered.

Why is there no backend?

The user often has no signal, so a server would make the app useless at the moment it's needed. One user and one device means nothing needs sharing. No server also means no accounts, no hosting costs and no personal data leaving the phone.

What would you do differently?

Do a real pitchside trial earlier, since the most useful feedback came from actually using it. And test in a real browser from day one, because the worst bugs were invisible to unit tests.

Did you use AI tools to build it?

Yes, Claude Code as a pair programmer. I set the goals and product decisions, reviewed the changes, tested in the browser, and documented the reasoning in a build journal. I can explain why each part works the way it does.

Machine learning

What is xG?

Expected goals: the probability a shot becomes a goal, based on how often similar shots scored in the past. A team's xG is the sum over its shots.

Which algorithm did you use and why?

LightGBM, a gradient-boosted decision tree library. It's very strong on tabular data, handles missing values natively, supports monotone constraints, and exports cleanly to ONNX. A geometry-only logistic regression was the baseline it had to beat.

Explain gradient boosting simply.

Build many small decision trees in sequence. Each new tree tries to correct the errors left by the trees so far. The final prediction combines all of them. A low learning rate means each tree only makes a small correction.

What data did you train on?

StatsBomb Open Data: 34,809 shots from 1,374 professional matches in 13 competitions. It includes freeze frames (positions of players at the moment of each shot), which match the keeper and defender markers in the app.

What are the most important features?

Distance to goal and shot angle (how wide a view of the goal the shooter has). After that: defenders in the shooting cone, keeper position, body part, and situation like open play or corner.

How did you handle missing inputs?

One adaptive model trained with feature-group dropout: each shot appeared in training in full, minimal, and three random partial versions with jittered marker positions. Then a separate isotonic calibration for each completeness bucket: minimal, partial and full.

What are monotone constraints?

Rules forcing the model's output to only move one way with a feature. Here, xG can't rise with distance or with defenders in the cone, and can't fall with a wider angle. It prevents nonsensical predictions from noisy data.

How did you split the data and why by match?

Train, validation, calibration and test sets (test 15%), assigned by a fixed hash of the match ID. Shots from the same match are correlated, so splitting by shot would leak information and make the test look better than it really is.

What is calibration and how did you do it?

Making predicted probabilities match real frequencies: 30% predictions should score about 30% of the time. I used isotonic regression fitted on held-out data, separately for each completeness bucket.

What is the difference between AUC and log loss?

AUC measures ranking: does a goal usually get a higher xG than a miss? Log loss measures the probabilities themselves and heavily punishes confident wrong ones. A model can rank well but be poorly calibrated, so both matter.

What were your results?

On 4,988 unseen shots with full inputs: log loss 0.263 (baseline 0.274), AUC 0.805, Brier 0.071, calibration-in-the-large 1.03 and correlation 0.90 with StatsBomb's own xG. Every bucket passed the release gate.

What is a release gate?

Pass/fail thresholds written into the spec before training. The model only ships if every completeness bucket meets every threshold and beats the baseline. It stops you moving the goalposts after seeing the results.

Why are penalties fixed at 0.76?

Penalties are nearly identical every time and their conversion rate is well known, so a model adds nothing. It's a documented exception.

What is PSxG?

Post-shot xG: how likely an on-target shot was to score given where it went in the goal. It's a second LightGBM model, trained on 12,423 on-target shots. It's optional and shown alongside xG, but doesn't change the verdict.

Did you compare other algorithms?

Yes: bagging, seed averaging, XGBoost and a random forest, with a paired bootstrap over test matches. None clearly beat the shipped model. A tuned LightGBM was 0.003 better in log loss, within seed noise, so I kept the original.

Is the "reason" text a model explanation?

No. It's a rule-of-thumb description of the inputs, like "close range, tight angle". A true explanation would need something like SHAP. I documented that distinction rather than overclaiming.

Web and engineering

What is your tech stack?

Frontend: React, TypeScript and Vite. Model inference: onnxruntime-web. Storage: IndexedDB through Dexie. Offline: a Workbox service worker. Training: Python with LightGBM, scikit-learn and pandas. Hosting: GitHub Pages, deployed by GitHub Actions.

How does the model run in the browser?

The trained model is exported to ONNX. onnxruntime-web loads it and runs it with WebAssembly. The TypeScript code computes the features from the taps, runs the model, then applies the calibration table.

How do you know the Python and TypeScript features match?

Parity tests. 48 real shots were run through the Python feature code and the outputs saved as fixtures. The TypeScript tests compute the same shots and fail if anything differs beyond rounding.

What is a component and a state in React?

A component is a reusable piece of UI, like the Pitch or the ShotEntry form. State is data that can change, like where markers are placed. When state changes, React redraws the affected components.

Why TypeScript instead of JavaScript?

Types catch mistakes before the code runs. For example, when new fields were added to the Match type, the compiler pointed to every place that needed updating.

What is IndexedDB and why not localStorage for shots?

IndexedDB is a proper database inside the browser that can store structured records and query them. localStorage only holds small strings, so it's used just for small settings like the last open match.

What is a service worker?

A background script that intercepts the site's network requests. Here it precaches the whole app and both models on the first visit, so everything works offline afterwards.

How is the site deployed?

A GitHub Actions workflow builds the app on each push and publishes the output folder to GitHub Pages. Because Pages serves from a sub-path, Vite's base path is set only when the GH_PAGES variable is present in CI.

How do users get updates?

The service worker auto-updates and reloads as soon as a new version is found while online. While offline it can't check, so the app shows a passive "may not be the latest version" note.

How did you test the app?

593 Vitest tests: feature parity, verdict and leaderboard logic, the database lifecycle with a fake IndexedDB, report HTML and clock logic. Plus manual walkthroughs in a real browser, which caught bugs the tests couldn't.

How did you make the page load faster?

Lazy-loaded the model runtime with a dynamic import so it isn't in the first download (main bundle 694 KB → 277 KB), and used the wasm-only build, halving the wasm file from 28 MB to 14 MB.

Why did the page freeze and how did you fix it?

onnxruntime-web defaulted to multi-threaded WebAssembly, which needs SharedArrayBuffer and COOP/COEP headers that GitHub Pages doesn't send. I set it to one thread and lazy-loaded the runtime.

Design

What are design tokens?

Named values (CSS variables) for colours, sizes and timings, defined once and reused everywhere. They keep the design consistent and easy to change.

How did you make it accessible for colour-blind users?

Every outcome has a unique shape as well as a colour, so colour is never the only signal. The palette was checked with an OKLab-based validator, which caught a violet/blue pair that collided under red-green colour blindness.

What does mobile-first mean?

Designing for a small phone screen first, then adapting for larger screens. The user is always on a phone, so big tap targets and a portrait pitch came first.

Why draw charts yourself instead of using a library?

The charts are simple, SVG keeps them sharp at any size, and the same drawing code is reused in the exported HTML report. It also avoids an extra download, which matters for an offline-first app.

Why was the background photo replaced?

Before making the repo public, its licence was checked and it was copyrighted. It was replaced with original vector art drawn in code, so nothing shipped has a licence problem.
